# Architecture Impact Report — ملف الموكل والملفات القانونية

> الإصدار الحالي: 4.2.0 — Schema v11 — التاريخ: 28/09/2026
> الهدف: `Client → ClientFile → LegalFile → Stage → Events` بدون حذف أي بيانات وبدون قاعدة بيانات جديدة.

---

## 2. الموجود حاليًا (ويطابق المواصفات بالفعل)

أغلب الأساس المطلوب موجود، والتطبيق لا يحتاج إعادة كتابة:

- **`files` هو فعليًا الـ LegalFile**: رقم داخلي مستقل، وحالة منفصلة عن المرحلة، ومحامٍ مسؤول، وأرشفة منفصلة عن الحذف المنطقي، وآخر نشاط، ونص بحث مطبّع.
- **`cases` هو فعليًا الـ Stage**: `stageType` و`numberType` و`caseNumber/caseYear` و`courtId` و`chamber` و`degree` و`stageOrder` و`status`. أي أن رقم القضية منفصل عن رقم الملف كما تطلب المواصفات (البند 16).
- **`fileParties`**: أطراف متعددة، وصفة الموكل مخزّنة في الطرف وليست في الموكل (البند 71 ✓).
- **`fileRelations`**: علاقات بين الملفات، وليس `parentFileId` فقط (البند 69 ✓).
- **`hearings` و`procedures` (الأعمال الإدارية) و`judgments` و`execution` و`documentReferences` و`activityLog`**: كلها مرتبطة بـ `fileId`، والقضائية منها بـ `caseId`.
- **Timeline موحد** في `services/timeline.js` (البند 83 ✓ جزئيًا).
- بيانات الموكل لا تتكرر، والملف يشير إلى الموكل (البند 7 ✓).
- لا يوجد store لكل نوع قضية (البند 95 ✓).

## 3. الفجوات (ما يجب تطويره أو إضافته)

| # | الفجوة | الأثر |
|---|---|---|
| G1 | لا يوجد **ClientFile** ولا **Client Code** (`CL-2026-000125`) | الملف القانوني يرتبط بالموكل مباشرة عبر `fileClients`، ولا توجد حاوية ولا لوحة لملف الموكل |
| G2 | **التصنيف ونوع العمل نصوص حرة** (`fileType`، `mainCategory`) وليست كيانات بمعرّفات | لا توجد شجرة تصنيف ← نوع، ولا ترتيب ولا أيقونة ولا تفعيل/تعطيل، وتغيير الاسم يكسر الإحصاءات |
| G3 | **الحقول الخاصة بالنوع ثابتة في الكود** (`FILE_TYPE_GROUPS` فيها 6 مجموعات فقط: civil وcriminal وfamily وadmin وexecution وconsultation) | لا يمكن إضافة «المحليات» أو «الضرائب» بحقولها من الإعدادات |
| G4 | **لا توجد Case Templates** ولا مسار مقترح | — |
| G5 | لا يوجد **`currentStageId`** على الملف | المرحلة الحالية غير محددة صراحة |
| G6 | المرحلة لا تحمل حالة دورة حياة (مخطط / جارية / منتهية / متخطاة) ولا نتيجة (outcome) | لا يمكن رسم ✓ ● ○ |
| G7 | ترقيم الملف `2026/0001` وليس `LF-2026-000731` | تغيير عرضي فقط، ويجب ألا يُعاد ترقيم الملفات القديمة |
| G8 | لا توجد كيانات **Property / Vehicle / Organization** | بيانات العقار والمركبة تُكتب في الملاحظات حاليًا |
| G9 | علاقات الملفات نص حر بدون اتجاه أو كود ثابت (`ORIGINATED_FROM` و`APPEAL_OF`...) | لا يمكن بناء «أنشئ ملفًا مرتبطًا» ولا عكس العلاقة |
| G10 | لا يوجد **Snapshot للأسماء** وقت التسجيل | تغيير اسم نوع أو مرحلة يغيّر المعنى التاريخي |
| G11 | الجلسة مرتبطة بـ `caseId` فقط وليس بـ `stageId` صريح | `caseId` هو المرحلة فعلًا، فيكفي توحيد المسمى في الواجهة |

## 4. القرار المعماري المقترح (بأقل كسر ممكن)

**مبدأ: إعادة تسمية مفاهيمية + إضافة، وليس إعادة كتابة.** أسماء الـ stores الحالية تبقى كما هي، لأن تغيير اسم store في IndexedDB يعني نسخ ملايين السجلات. الـ Repository يعرض الأسماء المفاهيمية الجديدة:

| المفهوم في المواصفات | الـ Store الفعلي | الإجراء |
|---|---|---|
| clients | `clients` | + `clientCode` (فريد) + index |
| **clientFiles** | **جديد** `clientFiles` | ملف رئيسي واحد لكل موكل (قابل لاحقًا لأكثر من ملف) |
| legalFiles | `files` | + `clientFileId` و`categoryId` و`fileTypeId` و`currentStageId` و`typeSnapshot` و`legalNumber (LF-…)` و`metadata` |
| fileStages | `cases` | + `stageTypeId` و`lifecycle` (planned/active/done/skipped) و`outcome` و`templateStepId` و`nameSnapshot` |
| fileParties / fileRelations | كما هي | + `relationCode` و`direction` للعلاقات |
| **workCategories / fileTypes / stageTypes** | **جديد** `taxonomy` (store واحد بـ `kind`) | الشجرة الكاملة للتصنيفات والأنواع (14 تصنيفًا افتراضيًا) قابلة للتعديل |
| **caseTemplates** | **جديد** `caseTemplates` | قوالب مقترحة، وكل خطوة `optional` |
| **fieldDefinitions** | **جديد** داخل `taxonomy` (`kind:'field'`) | حقول ديناميكية لكل نوع عمل (تخلف `FILE_TYPE_GROUPS` تدريجيًا) |
| properties / vehicles / organizations | **جديد** `assets` (بـ `kind`) + `fileAssets` (ربط) | عقار أو مركبة مرتبطة بأكثر من ملف |
| counters | `fileNumberCounters` | + مفاتيح `client:2026` و`lf:2026` |

### تخزين الحقول الديناميكية (بدون «JSON واحد»)
- قيم الحقول الخاصة بالنوع تُخزَّن **كحقول مسطحة على سجل الملف** بمفتاح ثابت (`f_policeStation` و`f_taxOffice`...)، كما يفعل التطبيق الآن مع `FILE_TYPE_GROUPS`. فتبقى قابلة للبحث والتصدير، ويدخل النص في `searchText`.
- الحقول المهمة التي يُبحث بها كثيرًا (رقم المحضر ورقم القضية والمحكمة) تبقى على المرحلة `cases`، وهي مفهرسة الآن.

### المسارات = اقتراح فقط
- القالب ينشئ مراحل بحالة `planned`، والمستخدم يحذف أو يضيف أو يتخطى أو يعيد الترتيب.
- لا توجد أي قاعدة من نوع «لا يمكن إنشاء استئناف». زر «+ مرحلة» يعرض كل الأنواع دائمًا.
- أزرار النتيجة (مثل «إحالة» أو «إحالة للمحكمة») تقترح **«إنشاء ملف مرتبط»** بعلاقة `ORIGINATED_FROM`، وتنسخ الأطراف فقط كروابط (بدون تكرار بيانات).

## 5. خطة الـ Migration (Schema v11 → v12)

1. **هيكلية (داخل `onupgradeneeded`)**: إنشاء `clientFiles` و`taxonomy` و`caseTemplates` و`assets` و`fileAssets`، وإضافة indexes: `clients.clientCode` و`files.clientFileId` و`files.categoryId` و`files.fileTypeId` و`files[clientFileId+categoryId]` و`cases.stageTypeId`. هذه الخطوة **إضافة فقط**.
2. **بيانات (بعد الفتح، عبر `runMaintenance` على دفعات بـ cursor، 200 سجل في كل معاملة، مع نسبة تقدم وقابلية للاستئناف بعد أي انقطاع عبر `meta.migrationV12Cursor`)**:
   - زرع التصنيفات والأنواع وأنواع المراحل والقوالب الافتراضية مرة واحدة.
   - لكل موكل: توليد `clientCode` (بالترتيب حسب `createdAt`) وإنشاء `clientFile`.
   - لكل ملف: ربطه بـ `clientFile` للموكل الأساسي (من `fileClients` أو `fileParties`)، وتحويل `fileType` النصي إلى `categoryId`/`fileTypeId` بجدول مطابقة (مثلًا «جنائي» ← criminal، و«أسرة» ← family، و«مجلس الدولة / إداري» ← stateCouncil، و«تنفيذ» ← التصنيف المناسب + نوع «تنفيذ»، والباقي ← «أخرى»)، مع **الاحتفاظ بالقيمة الأصلية** في `typeSnapshot`.
   - الملف الذي له أكثر من موكل: يُربط بملف الموكل الأساسي، ويظهر في ملفات الموكلين الآخرين عبر `fileParties` (بدون نسخ).
   - الملف بدون موكل: يبقى بدون `clientFileId` ويظهر في تقرير «ملفات بلا موكل» في صفحة سلامة البيانات.
   - `currentStageId` = آخر مرحلة حسب `stageOrder`، ثم `filingDate`.
   - **الملفات القديمة تحتفظ بأرقامها** (`2026/0001`) كـ `legalNumber`، والملفات الجديدة تأخذ `LF-2026-000001`.
3. **قبل الترحيل**: نسخة احتياطية JSON تلقائية إجبارية (خدمة `backup.js` موجودة)، مع رسالة للمستخدم.

## 6. مخاطر فقد البيانات والحماية منها

| الخطر | الحماية |
|---|---|
| انقطاع أثناء الترحيل | الترحيل البياني idempotent وعلى دفعات بمؤشر محفوظ، وإعادة تشغيله آمنة |
| تحويل نوع نصي خاطئ | القيمة الأصلية محفوظة في `typeSnapshot`، وتقرير «ملفات تحتاج تصنيفًا» لإعادة التصنيف يدويًا |
| تعارض `clientCode` | عداد داخل نفس المعاملة + index + فحص تكرار في صفحة سلامة البيانات |
| فتح التطبيق في تبويب قديم أثناء الترقية | `onversionchange` يغلق الاتصال القديم (موجود) |
| الأداء مع مئات الآلاف | لوحة ملف الموكل تقرأ بـ index `[clientFileId+categoryId]` وتعدّ بـ `count()` ولا تستخدم `getAll()`، والقوائم تستخدم `page(cursor)` + Virtual Scrolling (موجود) |
| حذف | **لا يوجد أي حذف** لأي store أو حقل. الحقول القديمة تبقى للقراءة |

## 7. مراحل التنفيذ المقترحة

| المرحلة | المحتوى | المخرجات |
|---|---|---|
| **P1 — الأساس** | Schema v12، وتعريف `taxonomy` وزرع 14 تصنيفًا بأنواعها، والعدادات `CL-` و`LF-`، وخدمة `clientFiles`، والترحيل على دفعات، واختبارات | لا تغيير مرئي تقريبًا، والبيانات مهيأة |
| **P2 — لوحة ملف الموكل** | زر «فتح الملف» في صفحة الموكل، واللوحة (هيدر وإحصاءات وبطاقات التصنيفات ← الأنواع ← الملفات)، وجدول للديسكتوب وبطاقات للموبايل، وآخر النشاط والجلسات والملفات المتوقفة | السيناريو 97 يظهر تحت كود واحد |
| **P3 — معالج «+ ملف قانوني»** | 3 خطوات (تصنيف ← نوع ← الحد الأدنى من البيانات) + «استخدام المسار المقترح / البدء يدويًا» | إنشاء ملف في أقل من 20 ثانية |
| **P4 — المراحل والقوالب** | شريط المراحل ✓ ● ○، وإضافة وإنهاء وتخطي وإعادة ترتيب، ونتيجة المرحلة، و«إنشاء ملف مرتبط» (إحالة / استئناف / تنفيذ)، وربط الجلسة والحكم بالمرحلة | مسارات مرنة |
| **P5 — الحقول الديناميكية والإعدادات** | محرر التصنيفات والأنواع والحقول والقوالب في الإعدادات، وتحويل `FILE_TYPE_GROUPS` إلى تعريفات افتراضية قابلة للتعديل | إضافة «الملكية الفكرية» بدون كود |
| **P6 — الأصول والبحث** | العقار والمركبة والمنظمة وربطها بالملفات، وتوسيع البحث (الكود، رقم المحضر، الخصم...)، واختبار 10+ ملفات لموكل واحد | اكتمال البنود 72–74 و85–86 و103 |
